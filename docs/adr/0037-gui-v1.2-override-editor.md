# ADR-0037 — GUI v1.2 Override Editor (Phase 11.3.2)

**Status**: Accepted
**Date**: 2026-05-03
**Deciders**: 사용자 (project owner)
**Related**: ADR-0033 (frontend topology / co-equal CLI+GUI),
ADR-0035 (v1 project-first surface), ADR-0036 (v1.1 Cutter workspace),
Phase 4A (stable identity contract), Phase 4B (override store),
Phase 11.4 (CLI override subcommand)

---

## Context

Phase 4B/4D/11.4 모두 override pipeline 을 구현 + CLI 측 검증 완료
(`aura override list/get/put/delete`). 그러나 GUI 측에서는 함수 이름
재정의 경로가 부재 — 사용자가 GUI 만으로 RE 작업을 끝낼 수 없다.

ADR-0033 의 "co-equal CLI + GUI on shared `aura_core`" 약속은 두
frontend 가 같은 데이터 모델 (`.aura.db`) 을 같은 의미로 다룬다는
의미. **GUI 가 override 를 다루지 못하면 그 약속은 표면적**. v1.2 의
목표는 GUI 가 CLI 의 `aura override put/delete` 와 동일한 효과를
사용자 클릭 한 번으로 달성하게 하는 것.

또한 향후 LLM rename 버튼 (Phase 11.3.3, "AURA killer feature") 의
저장소가 override_store — 그 UI 도입 전 manual override 가 선결.

## Decision

GUI v1.2 = **함수 이름 override editor** — 함수 list 우클릭 →
`Rename...` / `Reset name` → SQLite override_store 즉시 commit →
함수 list 갱신.

### v1.2 표면 (확정)

| 영역 | 결정 |
|------|------|
| 진입점 | 함수 list row **우클릭 context menu** (`Rename...` / `Reset name`). 인라인 셀 편집 거부 (실수 trigger 위험). |
| Rename dialog | `QInputDialog::getText` — 현재 이름 default + 새 이름 입력 + OK/Cancel. 별도 dialog 클래스 신설 X. |
| Override 종류 | **rename only** v1.2. type / annotation = v1.3+. (Phase 4B `AURA_OVERRIDE_PAYLOAD_RENAME` 에 한정.) |
| Persistence | **즉시 commit** (Phase 11.4 정책 일관, dirty 상태 부재). |
| 시각 표시 | 함수 list `Name` 컬럼에 **override 이름** 그대로 표시. tooltip = 원래 engine 이름. `Source` 컬럼에 `"user/rename"` 표기 (override 적용된 행). |
| Stable_id 계산 | CLI 의 `build_rich_key` 추출 → `aura_override_identity_build_function_key()` 라이브러리 API 신설. CLI + GUI 양쪽 동일 호출. |
| Override store 연결 | 같은 `.aura.db` (Project = 단일파일, ADR-0035). MainWindow 가 `aura_override_store_open()` 으로 별도 핸들 보유 (project_binaries 와 독립). |
| Reset (delete) | `Reset name` → `aura_override_store_delete()` → reload. rename 의 역연산. |
| Conflict UX | v1.2 미처리 — Phase 4C/4D resolve pipeline 의 conflict/orphan 상태는 CLI 에서만 노출. GUI 별도 view = v1.3+. |
| Override 전체 list dock | **없음** v1.2. 함수 list 의 Name 컬럼이 override 적용 후 보임 → 별도 view 불필요. v1.3+ "All Overrides" dock 추가 가능. |
| GUI 시작 시 / 분석 후 적용 | 분석 직후 + 매 override 변경 후 `apply_overrides_to_functions()` 실행 — 함수 record 의 name 을 user override 로 치환. |

### Override key 구성 (CLI 와 동일)

```
key.binary_fingerprint = sha256(binary_path)  ← 이미 project_binaries 에 저장
key.engine_id          = "rizin"
key.engine_version     = adapter manifest version
key.body_schema_version = AURA_RIZIN_ANALYZE_BODY_VERSION
key.norm_record_schema_ver = NORMALIZED_RECORD_VERSION
key.request_type       = AURA_ENGINE_REQ_ANALYZE
key.function_stable_id = stable_id_from(function_record)  ← Phase 4A
key.target_kind        = AURA_OVERRIDE_TARGET_FUNCTION_NAME
key.target_stable_id   = function_stable_id (rename = self-target)
key.target_addr        = function_record.entry
key.engine_record_source_id = 0
key.confidence         = AURA_OVERRIDE_CONFIDENCE_USER
```

### v2+ 로 분리 (의도적 누락)

- Type override (변수/함수 시그니처)
- Comment / annotation override
- Override 전체 list dock
- Conflict / orphan 시각화 dock
- Undo stack
- 일괄 rename / 정규식 rename
- LLM rename 버튼 (Phase 11.3.3 — 본 ADR 의 직접 후속)

## Rationale

### Override editor 가 LLM rename 보다 먼저인 이유

LLM rename = LLM API 호출 + 응답 파싱 + override 저장. 마지막 단계
(저장) 가 manual override 와 동일 path. **manual override 가 작동
안 하면 LLM 결과를 어디에 저장할지 결정 불가**. v1.2 가 v1.3 의
저장 인프라.

### 우클릭 context menu vs 인라인 셀 편집

인라인 = QTableView 의 Qt::ItemIsEditable flag — 셀 더블클릭으로
진입. 사용자가 단순 행 선택 의도였는데 더블클릭 → 분석 dialog 가
열림 (v1.1 의 더블클릭 = 분석). 동작 충돌.

우클릭 context menu = 명시적 의도, RE 도구 (Ghidra/Cutter) 표준,
충돌 없음.

### `aura_override_identity_*` 라이브러리화 (CLI 코드 복제 거부)

CLI 의 `build_rich_key()` (`src/cli/main.cpp`) 는 rename / put /
delete 모두 사용. GUI 가 별도 구현 시 두 곳에서 stable_id 계산 — 한
쪽이 미세 변경되면 두 frontend 가 다른 키로 동작 = co-equal contract
파괴. 라이브러리화로 단일 진실 source.

### 즉시 commit (Save 버튼 거부)

Phase 11.4 의 CLI override = 즉시 commit. GUI 도 같은 정책 = co-
equal. Save 버튼 도입 시 dirty 상태 추적 + close confirm 등 결정
폭증.

### 함수 list Name 컬럼에 override 이름 (별도 컬럼 거부)

별도 컬럼 (예: "Override name") = 사용자가 두 컬럼 다 봐야 함, 가독성
저하, 컬럼 수 증가. user override 가 "사용자 의미" — 그 의미가
일차적이라 Name 컬럼 자체를 user 의 답으로 표시. 원래 이름은 tooltip
+ Source 컬럼의 "user/rename" 표기로 명확.

### Override 전체 list dock 미도입

함수 list = override 가 적용된 view. 별도 dock = 같은 데이터의 다른
표현 = 정보 중복. v1.3+ 에서 "rename 된 함수만 필터링" 등 가치
명확해진 후 도입.

## Consequences

### Positive

- **Co-equal contract 의 GUI 측 realize** — Phase 4B/11.4 가 표면적이
  아닌 실질적 양립.
- LLM rename 버튼 (Phase 11.3.3) 의 저장 인프라 완비.
- AURA 차별점 영역의 1차 GUI 검증.
- `aura_override_identity_*` 라이브러리화 = CLI 코드도 정리 (DRY).

### Negative

- 함수 list reload 가 매 override 변경 시 수행 = 분석 결과 N개 함수에
  대해 N rows reload. v1.2 에서 N ≤ ~수천 정도면 즉각 응답.
- Override 가 rename 만 → type/annotation 사용자 요구 시 v1.3 까지
  대기.

### Neutral

- `aura_override_store_open()` 이 project DB 와 같은 파일을 두 핸들로
  열음 — SQLite 멀티 핸들 안전 (이미 검증된 패턴).

## Alternatives Considered

### 인라인 셀 편집 (Qt::ItemIsEditable)

거부. 더블클릭 분석 dispatch 와 충돌 + 실수 진입 위험.

### 별도 "Override editor" dock

거부. v1.2 scope 폭발 — dock 자체의 layout / state / 함수 list 와의
binding 결정 라운드 N개. 우클릭 menu = 즉시 가치, scope 최소.

### Save 버튼 + dirty 상태 추적

거부. Phase 11.4 정책과 비일관 + close confirm 등 결정 폭증.

### CLI 의 build_rich_key 그대로 복사 (라이브러리화 회피)

거부. co-equal contract 파괴 위험. v1.4+ 에 stable_id 알고리즘 변경
시 두 frontend 가 다른 키 사용 = 사용자 데이터 손실 가능.

## Implementation

Slice 단위:
- **A** — ADR-0037 + ROADMAP + CONTEXT (본 커밋)
- **B** — `aura_override_identity_build_function_key()` API 추출
  (include/override_identity.h 확장 + src/cli/main.cpp 호출 갱신)
- **C** — MainWindow 에 `AuraOverrideStore*` 보유 + open/close 연동
- **D** — `FunctionTableModel` 의 setFunctions() 직후 override 적용
  (rename name 치환 + Source 컬럼 "user/rename" 표기)
- **E** — 함수 list 의 `customContextMenuRequested` 시그널 + menu
  (Rename / Reset)
- **F** — Rename `QInputDialog` + `aura_override_store_put()` 호출 +
  Reset 시 delete 호출 + 양쪽 모두 reload
- **G** — `gui_smoke` 확장: rename round-trip (put → reload → 새 이름
  표시 → reset → 원래 이름 복귀)
- **H** — Tier 1 ctest 양립 확인

Phase 11.3.3 (LLM rename 버튼) 은 별도 ADR + slice. 본 ADR 의 v1.2
완료 후.
